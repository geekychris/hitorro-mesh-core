== About this guide

Hitorro Mesh is a *Spark-like distributed SQL engine* built on the
Hitorro stack. It layers per-partition query execution (jvssql), a
wire-transport SPI (NATS by default), and a coordinating driver over
an already-existing JSON-typed data platform. This guide walks through

  API summary, metrics catalogue.

= Part I — Architecture

[#what-mesh-is]
== What the mesh is (and isn't)

*What it is.* A thin coordination layer that takes a SQL query at the
driver, splits it into per-partition tasks, dispatches them to a fleet
of agent JVMs over NATS, and merges results back to the client. Each
agent runs an embedded jvssql engine over its local slice of data. The
mesh speaks JSON on the wire (JVS-typed documents), doesn't require a
shared storage layer, and treats every module as an independent Git repo
and Maven artifact.

*What it isn't.* A full replacement for Spark or Flink. It doesn't have
a fault-tolerant distributed cache, a lineage-tracking DAG optimizer, a
Python or R client, or years of SQL query-optimizer tuning. It is
*purpose-built for Hitorro-shape workloads*: querying typed JSON
documents across horizontally-sharded stores, with optional streaming
ingest and long-lived windowed aggregates.

=== When to pick the mesh vs Spark or Flink

An honest tradeoff table — not "who has more features" but "where does
each fit best."

[cols="3,3,3,3", options="header"]
|===
| Concern | Mesh | Spark | Flink

| Deployment overhead
| Just JVMs + NATS. No cluster manager.
| Needs YARN / K8s / Standalone cluster.
| Needs its own JobManager / TaskManager cluster.

| Startup cold time
| ~2 seconds (fat-jar JVM start)
| ~30 seconds (cluster spin-up)
| ~10 seconds

| Bundle size on disk
| ~65 MB per fat-jar
| ~800 MB+ install
| ~500 MB

| Query planner sophistication
| Regex-based, no cost model — good for simple/known workloads
| Full cost-based optimizer + Catalyst
| Full cost-based optimizer

| Client languages
| HTTP (any language) or embedded Java
| Python, R, Scala, Java, SQL client
| Python, Scala, Java, SQL client

| Stateful streaming (checkpoints, savepoints)
| ❌ Not supported
| ✅ Structured Streaming
| ✅ Native — production streaming systems' default

| Native support for typed JSON documents
| Deep (JVS types, `jvssql`)
| Via schema inference or explicit case classes
| Via Table API schema

| SLA target
| Sub-100ms query latency achievable
| Seconds to minutes typical
| Sub-second achievable

| Best fit
| Distributed SQL over JVS-typed JSON, embedded or standalone; teams that don't want cluster-manager complexity
| Batch + interactive SQL on huge data; ML pipelines
| High-throughput long-lived streaming with exactly-once semantics
|===

The mesh is *purpose-built for one thing very well:* distributed SQL
over typed JSON documents, at low deployment cost, with real production
plumbing (metrics, retries, timeouts, cancels, hardened deploys). It's
not trying to replace Spark or Flink at their strengths.

=== Design principles

* *Modular by default* — every capability (streaming, orion bridge, k8s
  bridge, kafka adapter, TLS) lives in its own optional module.
* *Wire-narrow* — the transport SPI has exactly two methods
  (publish, subscribe). That's enough to add a new transport with ~100
  lines of code.
* *Pluggable plan variants* — a sealed `Plan` interface with one
  variant per execution shape. Adding a new shape means adding a new
  sealed subclass + a dispatcher method.
* *Fail-visible not fail-fast* — typed exceptions, an EXPLAIN endpoint,
  a health indicator with per-partition detail. Operators can see WHY
  a query failed without grep'ing logs.

*Roles:*

* *Client* — anything that speaks HTTP. Batch mode sends a POST and
  waits; streaming mode holds an SSE connection open. The client can
  also cancel via `DELETE`.
* *Driver* — one per mesh. Owns the query planner, the agent
  registry (agents heartbeat to it), the distributed-table registry
  (what's queryable), and the REST surface. Stateless with respect to
  query state; can be restarted without losing data (queries in flight
  fail, retry-on-client if configured).
* *Agents* — N per mesh. Each declares its capabilities (`jvssql`,
  `partition:docs:us`, etc.) and heartbeats to NATS. When a task
  arrives, it executes against the agent's `LocalTable` set and
  results publish back.
* *NATS* — the only cross-process communication path. Uses subject
  conventions (see next section). Optional TLS + auth via
  `NatsSecurityProperties`.

[#wire-protocol]
== Wire protocol

The mesh's wire surface is deliberately narrow — five message types
on four well-known subject patterns.

=== Message types

[cols="1,3", options="header"]
|===
| Type | Purpose

| `HeartbeatMessage`
| Agent → driver, periodic. Announces the agent is alive with its
  current capability set.

| `TaskDescriptor`
| Driver → specific agent. Carries the SQL to run, source table +
  partition key, required capabilities, result subject, optional
  shuffle spec, optional combine spec.

| `ResultMessage`
| Agent → driver. Four kinds: `ROW` (a result document), `EOS`
  (end-of-stream for this partition), `ERROR` (agent-side failure),
  `WATERMARK` (streaming heartbeat with max observed event-time).

| `CancelMessage`
| Driver → all agents for a query. Interrupts in-flight tasks for
  that queryId; agents publish EOS and cleanup.

| `AgentDescriptor`
| Driver-side record derived from `HeartbeatMessage` — what the
  driver knows about each live agent.
|===

=== Subject conventions

[cols="1,2", options="header"]
|===
| Subject pattern | Direction / purpose

| `mesh.agent.heartbeat.<agentId>`
| Agent → driver (via wildcard subscription `mesh.agent.heartbeat.*`)

| `mesh.agent.task.<agentId>`
| Driver → specific agent

| `mesh.query.result.<queryId>.<partitionKey>`
| Agent → driver (driver subscribes to `mesh.query.result.<queryId>.*`)

| `mesh.query.control.<queryId>`
| Driver → agents (cancel signal)

| `mesh.query.shuffle.<queryId>[.<sideLabel>].<bucket>`
| Agent → agent (shuffle-hash join / distributed combine)
|===

*Selection rules* (in order):

. Streaming source AND `WIN_START` in `GROUP BY` → `StreamingWindowedPlan`
  (dispatcher branches on partition count).
. Two-distributed-table JOIN detected (`FROM a JOIN b ON a.k = b.k`):
  * With `GROUP BY` / aggregate → `ShuffleJoinAggregatePlan`
  * Otherwise → `ShuffleJoinPlan`
. `GROUP BY` / aggregate / `SELECT DISTINCT` → `TwoStagePlan`
. Otherwise → `SimplePlan`

== Two-stage combine (batch aggregate)

The most common non-trivial shape: `GROUP BY` + aggregates without a
join. Each partition computes partial aggregates locally, driver
reduces across partitions using SUM-for-SUM/COUNT, MIN-for-MIN,
MAX-for-MAX, SUM/COUNT-for-AVG (AVG decomposes to two partial
columns).

FROM ...` and `SELECT lang AS L, COUNT(*) AS n FROM ...` return
sensibly-named columns.

Fact × fact join between two distributed tables. Both sides shuffled

do the actual join.

== Stage 1: combines subscribe first ==
D -> CA : TaskDescriptor(stage=1, combine bucket 0)
D -> CB : TaskDescriptor(stage=1, combine bucket 1)
CA -> CA : subscribe left.0 + right.0
CB -> CB : subscribe left.1 + right.1

D -> SA : TaskDescriptor(stage=0, scan docs, shuffleSpec left)
D -> SB : TaskDescriptor(stage=0, scan events, shuffleSpec right)
SA -> CA : rows for bucket 0\n(hash(docs.id) mod 2 == 0)
SA -> CB : rows for bucket 1
SA -> D : partition EOS
SB -> CA : rows for bucket 0
SB -> CB : rows for bucket 1
SB -> D : partition EOS

== Stage 1 execution ==
CA -> CA : join SQL runs locally\nover both buffered sides
CA -> D : result rows + EOS
CB -> CB : same for bucket 1
CB -> D : result rows + EOS

@enduml
....

*When both sides shuffle* (as shown), each combine worker sees only
matching join keys from BOTH tables — perfect for a hash join. The
`CombineSpec` carries per-side type JSON (phase 4c.1) so empty
buckets can register a typed-but-empty stream for OUTER JOIN
semantics.

*With aggregates* (`ShuffleJoinAggregatePlan`), stage 1 emits partial
aggregate rows; stage 2 runs at the driver to reduce partials across
buckets. WHERE clauses that reference only one side of the join push
down to that side's scan task (phase 4b.2.1), cutting shuffle
bandwidth for filter-heavy queries.

[#multi-partition-close]
== Multi-partition close detection

Detail on how the driver decides a window is "closed globally" across
all streaming partitions. Combines phase-6d.2 emission-based tracking
with phase-6d.2.1 watermark heartbeats and phase-6d.2.2 idle-timeout
watermarks — no single input alone is authoritative.

[plantuml, multi-partition-close, svg]
....
@startuml
skinparam backgroundColor transparent
skinparam defaultFontName Helvetica
skinparam defaultFontSize 12
skinparam roundCorner 6
skinparam shadowing false
skinparam ArrowColor #333
skinparam state {
  BackgroundColor #E8F1F5
  BorderColor #2E86AB
  FontColor #333
  ArrowColor #444
}

[*] --> Buffering

state "Buffering partials" as Buffering {
  Buffering : Per partition:
  Buffering :   latestWindow[p] = MIN_VALUE
  Buffering :   rowsBuffered = 0
}

Buffering --> AdvanceOnRow : ROW arrives\n(window_start = W)
AdvanceOnRow : latestWindow[p] = max(latest, W)
AdvanceOnRow : buffer.add(window, partialRow)
AdvanceOnRow --> CheckClose

Buffering --> AdvanceOnWatermark : WATERMARK arrives\n(watermarkMs = wm)
AdvanceOnWatermark : latestClosed = ((wm − size) / size) * size
AdvanceOnWatermark : latestWindow[p] = max(latest, latestClosed)
AdvanceOnWatermark --> CheckClose

CheckClose : Compute minLatest = min(latestWindow across all partitions)
CheckClose --> EmitWindows : minLatest ≥ oldestBufferedWindow
CheckClose --> Buffering : otherwise

state "Emit closed windows" as EmitWindows {
  EmitWindows : For each buffered window W where W ≤ minLatest:
  EmitWindows :   run combineSql over buffer[W]
  EmitWindows :   emit result rows to client
  EmitWindows :   remove W from buffer
}

EmitWindows --> Buffering

Buffering --> Terminate : all partitions EOS\n or CancelMessage
state "Terminate" as Terminate {
  Terminate : drainAll = true
  Terminate : flush every remaining buffered window
  Terminate : emit final EOS
}
Terminate --> [*]

@enduml
....

*Why three signals* (row / watermark heartbeat / idle timeout):

* *Row emissions* — a partition emitting for window W proves its
  watermark advanced past W's end. Cheapest signal but only fires
  when the partition has data in a window.
* *Watermark heartbeats* — a periodic ~200ms publish of the
  partition's max observed event-time. Advances closure even when a
  partition observes events but hasn't crossed a window boundary
  since its last emission.
* *Idle-timeout watermarks* — after the partition is silent for
  `hitorro.mesh.watermark.idle-timeout-ms`, its watermark auto-advances
  based on wall-clock. Prevents pure-idle partitions from stalling
  global window closure indefinitely.

[#retry-model]
== Retry model

The mesh has two independent retry layers, applied in this order on a
transient agent failure:

[plantuml, retry-state-machine, svg]
....
@startuml
skinparam backgroundColor transparent
skinparam defaultFontName Helvetica
skinparam defaultFontSize 12
skinparam roundCorner 6
skinparam shadowing false
skinparam ArrowColor #333
skinparam state {
  BackgroundColor #E8F1F5
  BorderColor #2E86AB
  FontColor #333
  ArrowColor #444
}

[*] --> Submitted

state "Submitted" as Submitted {
  Submitted : REST controller receives POST
  Submitted : timeoutMs, retries N from body
  Submitted : whole-query attempt = 1
}

Submitted --> Executing

state "Executing" as Executing {
  Executing : Dispatcher fans tasks to partitions
  Executing : Each task: task-attempt = 1
}

Executing --> OK : all partitions emit EOS\ncleanly
Executing --> PartitionError : one partition emits ERROR

state "Partition error" as PartitionError {
  PartitionError : rows-emitted == 0?
  PartitionError : task-attempts < maxTaskRetries?
}

PartitionError --> RetryTask : yes, both
RetryTask : re-dispatch same partition\non fresh agent pick
RetryTask : task-attempts++
RetryTask --> Executing

PartitionError --> QueryError : no (already emitted rows,\n or task budget exhausted)

state "Query error" as QueryError {
  QueryError : AgentTaskException raised
}

QueryError --> RetryQuery : whole-query attempts < 1 + N
RetryQuery : sleep 100 · 2^attempt ms
RetryQuery : whole-query attempt++
RetryQuery : fresh queryId, fresh dispatch
RetryQuery --> Submitted

QueryError --> Fail : whole-query budget exhausted

state "OK" as OK {
  OK : QueryResponse to client
  OK : with attempts = final count
}
state "Fail" as Fail {
  Fail : AgentTaskException → 502 Bad Gateway
  Fail : via MeshExceptionHandler
}

OK --> [*]
Fail --> [*]

@enduml
....

*Configuration.*

* Task-level retry cap: `-Dhitorro.mesh.driver.max-task-retries` (default 1).
* Whole-query retry cap: REST request body `{"retries": N}` (default 0).

The two are independent; whole-query retry kicks in after the task-level
budget is exhausted OR when the failure isn't retryable at the task level
(e.g. rows already emitted).

= Part III — Query language

[#sql-cheat-sheet]
== SQL cheat sheet

Everything the mesh distributes. Every row includes a worked example.

[cols="2,3", options="header"]
|===
| Shape | Example

| Filter + projection
| `SELECT id, title FROM docs WHERE lang = 'en'`

| GROUP BY + aggregate
| `SELECT lang, COUNT(*) FROM docs GROUP BY lang`

| DISTINCT (auto-rewritten to GROUP BY)
| `SELECT DISTINCT lang FROM docs`

| HAVING
| `SELECT lang, COUNT(*) c FROM docs GROUP BY lang HAVING c > 10`

| AVG (decomposes to SUM+COUNT partials)
| `SELECT lang, AVG(size_kb) FROM docs GROUP BY lang`

| LIMIT + ORDER BY (with pushdown + N-way merge)
| `SELECT id FROM docs ORDER BY size_kb DESC LIMIT 10`

| Broadcast INNER JOIN
| `SELECT d.id, l.name FROM docs d JOIN langs l ON d.lang = l.code`

| Broadcast OUTER JOIN (LEFT / RIGHT / FULL)
| `SELECT d.id, l.name FROM docs d LEFT JOIN langs l ON d.lang = l.code`

| Shuffle-hash JOIN (both distributed)
| `SELECT d.id, e.action FROM docs d JOIN events e ON d.id = e.doc_id`

| Shuffle-hash + WHERE (per-side pushdown)
| `... WHERE d.title = 'X' AND e.action = 'view'`

| Shuffle-hash + GROUP BY (3-stage combine)
| `SELECT d.lang, COUNT(*) FROM docs d JOIN events e ON d.id = e.doc_id GROUP BY d.lang`

| Global aggregate (single-row output)
| `SELECT COUNT(*) FROM docs JOIN events ON docs.id = events.doc_id`

| Windowed aggregate (batch or streaming)
| `SELECT WIN_START(event_time, 60000) ws, COUNT(*) n FROM events GROUP BY WIN_START(event_time, 60000)`
|===

*Aliases* — the mesh preserves `AS foo` aliases through combine SQL
(phase 6d.2.3). `SELECT lang AS L, COUNT(*) AS cnt` returns columns
named `L` and `cnt`, not the internal `g0`/`c0` fallbacks.

*Not distributed (yet):*

* Streaming JOIN between two streaming sources (planned phase 8)
* Subqueries in the WHERE / SELECT list
* Window functions (`OVER PARTITION BY`)
* PIVOT / UNPIVOT
* CTEs (`WITH x AS ...`)
* Correlated queries

[#storage-layer]
== Storage — local files + S3/MinIO

The mesh reads and writes through a single `BaseFile` abstraction so
every path — dataset NDJSON, query-result export, browser walk — routes
uniformly by URI scheme:

[cols="1,3", options="header"]
|===
| Scheme | Backend
| `file:/…` | local filesystem (default when no S3 is configured)
| `s3://…`  | MinIO / S3-compatible endpoint via `MinioProtocolAdapter`
| `hdfs://…` | Hadoop DFS via the HDFS adapter
| `ftp://…`  | FTP via the FTP adapter
|===

Same `getBaseFileFromPath(url)` call at the read + write sites — no
scheme-specific branches in caller code.

=== Configuring S3/MinIO

Set these env vars (or `hitorro.storage.s3.*` properties) before
starting the driver. The `S3StorageAutoConfig` bean registers the
adapter at boot when `HITORRO_STORAGE_S3_ENDPOINT` is present:

[source,bash]
----
export HITORRO_STORAGE_S3_ENDPOINT=http://localhost:9000
export HITORRO_STORAGE_S3_ACCESS_KEY=hitorro
export HITORRO_STORAGE_S3_SECRET_KEY=hitorro-dev-only
export HITORRO_STORAGE_S3_BUCKET=hitorro
----

Every `s3://bucket/key` URI passed through the driver then routes to
that endpoint. Absence of the endpoint = local-only mode (no error).

=== Starting MinIO for local development

MinIO is the recommended dev-time S3-compatible server — a single
Docker container backed by a named volume. Two ways to bring it up:

**From the UI (one click, hot-switches the running driver):**

Cluster tab → Storage card → *▶ Start MinIO*. The driver

. runs `hitorro-mesh-examples/scripts/minio/minio-up.sh` (pulls the
  image on first click, ~30 s; subsequent starts are seconds because
  the container persists)
. polls `http://localhost:9000/minio/health/live` until 200
. constructs a `MinioProtocolAdapter` and calls
  `BaseFileSystem.addProtocolAdapter(...)` — every subsequent `s3://`
  lookup now resolves through MinIO, *no driver restart*
. registers the adapter as a Spring singleton so
  `ObjectProvider<MinioProtocolAdapter>` injections (StorageService,
  QueryWriteController) pick it up immediately

The button status flips to `running` and the detail line shows
endpoint, bucket, console URL, credentials.

**From the shell (persistent across driver restarts):**

[source,bash]
----
cd hitorro-mesh-examples/scripts/minio
./minio-up.sh           # brings container up + creates bucket
./minio-sync-datasets.sh  # copies ~/.hitorro/datasets → s3://hitorro/datasets/
./minio-down.sh         # docker compose down (data persists in volume)
----

Defaults (all overridable via `HITORRO_MINIO_*` env vars):

[cols="1,2", options="header"]
|===
| Setting | Default
| S3 API endpoint  | `http://localhost:9000`
| Web console      | `http://localhost:9001` (login `hitorro` / `hitorro-dev-only`)
| Root user        | `hitorro`
| Root password    | `hitorro-dev-only`
| Bucket           | `hitorro`
|===

=== Storage summary + browser (Cluster tab)

The Storage card in the UI aggregates both backends and lets you walk
the tree without leaving the driver:

* **Local** — `~/.hitorro/datasets` file count + byte size
* **MinIO / S3** — endpoint, bucket, reachability
* **Dataset presence matrix** — per-dataset `local` vs `MinIO`
  checkmarks (only shown when both are configured), so you can spot
  what hasn't been synced yet
* **Browse** — click into any prefix; breadcrumb navigation preserves
  the scheme (`s3://`, `file:/`); the `↑ up` link uses the server's
  computed parent so it always resolves

Backed by `GET /mesh/storage` (summary) and
`GET /mesh/storage/browse?path=…` (walk). The browse endpoint
uses `BaseFileSystem.getBaseFileFromPath(...)` so local dirs and S3
prefixes render identically.

[#runtime-tables]
== Runtime table registration

The Playground's write panel has a *Register as broadcast table*
checkbox. Tick it (optionally supply a table name), click Write, then
run `SELECT * FROM <name>` immediately — no restart, no config edit.

The flow spans three moving parts:

. **Driver-side dual registration.** The driver adds the name to its
  broadcast set (so planner-side JOIN validation accepts it) AND
  registers a single-partition distributed table with only the
  `jvssql` capability (so `SELECT * FROM x` routes to any live
  jvssql agent). Mirrors what `MeshRegistrar.registerBroadcastAsDistributed`
  does for shipped datasets.

. **Fan-out via NATS.** The driver publishes a
  `RegisterTableMessage(name, typeJson, uri, format, broadcast, partitionKey)`
  on `mesh.agent.control.register-table`. Every live agent subscribes
  to that subject and installs the referenced file in its
  `RuntimeTableRegistry`.

. **Agent-side install.** `RuntimeTableInstaller` builds an
  `NdjsonLocalTable` or `ParquetLocalTable` from the URI + format,
  registers it in the agent's runtime registry under BOTH `pk=null`
  (for JOIN broadcast enumeration) and `pk="broadcast"` (for direct
  `SELECT * FROM x` scan). The `TaskExecutor.requireLocalTable` +
  `engineWithBroadcasts` lookups check the runtime registry FIRST,
  so a runtime entry with a given name shadows any boot-time entry.

**Type induction.** The driver induces the JVS type from the first
result row — every column becomes a nullable `core_string` /
`core_long` / `core_double` / `core_boolean` based on the JsonNode
kind. Nested objects fall back to `core_string`. Good enough for
ad-hoc query-result tables; for strict typing, build the type
yourself and hit `POST /mesh/tables` directly.

**S3-backed writes need agents to have the S3 adapter.** If the
driver has S3 configured but agents don't, the runtime registration
still succeeds at the driver, but the agent-side install fails when
the URI is `s3://…`. The `Start MinIO` button fixes this in the same
click — see next section.

**Persistence across agent restarts.** Every install writes an
NDJSON record to
`${hitorro.agent.home}/runtime-tables/<agentId>.jsonl`
(default `~/.hitorro/agent/runtime-tables/<agentId>.jsonl`). On boot,
`RuntimeTableInstaller.start()` dedups the journal by (name,
partitionKey), drops entries with later tombstones, and reinstalls the
surviving set BEFORE opening the live NATS subscription. Agents rejoin
the mesh with the same runtime tables they had before the restart.

**Unregister flow — symmetric.** `DELETE /mesh/tables/{name}` (or
`DELETE /mesh/broadcast-tables/{name}`) removes the driver-side entry
AND publishes an `UnregisterTableMessage` on
`mesh.agent.control.unregister-table`. Every live agent drops the
runtime install from both partition slots (pk=null + pk="broadcast")
and appends a tombstone to its journal so the entry doesn't
resurrect on the next boot.

**Listing what's runtime-registered.** `GET /mesh/queries/registered`
returns the driver-side memory of tables registered via the write
panel: `[{name, uri, format, typeJson, broadcast, partitionKey,
agentsNotified, registeredAt}]`. Backed by an in-memory
`RuntimeTableTracker` — driver-restart clears the list, but agents
keep their durable journal so tables stay queryable across the
bounce; the list just re-populates as new registrations arrive.

The Playground tab renders this as a "Runtime-registered tables"
fieldset (hidden when empty), one row per table with a ▶ button
that pastes `SELECT * FROM <name> LIMIT 100` into the editor and a
🗑 button that unregisters (with confirm).

**Journal compaction.** On boot, after replay,
`RuntimeTableJournal.compact()` rewrites the file to contain only
the currently-active register records — tombstones and superseded
entries are dropped. Atomic-rename via `.tmp` sibling so a crash
mid-compaction leaves either the old journal or the new one, never
a partial file. Only fires when there's more than a handful of lines
to save (avoid churn on already-tight files).

[#s3-hot-switch]
== S3 hot-switch — one click enables the whole mesh

The driver's `Start MinIO` button doesn't just wire the driver's own
S3 adapter — it also publishes an `EnableS3Message(endpoint, bucket,
accessKey, secretKey, ssl)` on `mesh.agent.control.enable-s3`. Every
live agent subscribes to that subject via `S3AdapterInstaller` and
installs the same `MinioProtocolAdapter`. Result: `s3://…` URIs
resolve on every agent's `BaseFileSystem.getBaseFileFromPath()` from
that moment on.

Without this, agents that boot without `HITORRO_STORAGE_S3_ENDPOINT`
can't read `s3://` runtime-registered tables — they'd only see the
enable-s3 message if they were listening. With it, the whole loop
works: click Start MinIO → write `SELECT` to `s3://` → register as
broadcast table → `SELECT * FROM <name>` returns rows from an agent
reading the s3 file.

Credentials cross the wire. Use TLS + NATS auth
(<<NatsSecurityProperties — auth + TLS>>) when the mesh isn't
localhost-only.

[#query-export]
== SELECT → file / S3 (query export)

The Playground has a *Write results to storage* panel that runs your
SQL and streams the rows to an NDJSON or Parquet file. Bare names
resolve to a sensible default; explicit URIs pass through:

[cols="2,3", options="header"]
|===
| Path field           | Where it writes to
| `my-langs`           | `s3://<bucket>/queries/my-langs.<format>` (S3 configured), else `file:/<cwd>/queries/my-langs.<format>`
| `file:/tmp/out.ndjson` | `/tmp/out.ndjson` (passthrough)
| `s3://mybucket/x.parquet` | that exact key (passthrough)
| `hdfs://nn:9000/…`   | HDFS via the HDFS adapter
|===

The Format dropdown picks the sink:

* **ndjson** — one JSON per line via `NdjsonFileSink` (local `file:`) or
  `BaseFileNdjsonSink` (`s3://`, `hdfs://` — routes through
  `BaseFile.getOutputStream()`). `.gz` extension → gzip.
* **parquet** — via `ParquetFileSink` from the `hitorro-streams-parquet`
  module. Schema induced from the first row (nullable typed columns for
  scalars, string fallback for nested). Requires `hitorro-streams-parquet`
  on the classpath — the driver-app bundles it. For `s3://` targets the
  controller rewrites the URI to `s3a://` and injects a Hadoop
  `Configuration` carrying the driver's MinIO endpoint + credentials +
  path-style-access, so the write hits the same bucket as the rest of
  the mesh.

A live-preview line under the input calls
`GET /mesh/queries/write/resolve?path=…&format=…` on every keystroke so
you always know where the bare name will land before clicking Write.
The write response includes the resolved URI in the success message.

**REST directly** — POST body shape:

[source,json]
----
{
  "sql":       "SELECT alpha3, reference_name FROM iso_639_3 LIMIT 5",
  "format":    "ndjson",
  "path":      "my-langs",
  "timeoutMs": 60000,

  "register":  true,          // OPTIONAL — install as broadcast table on every agent
  "tableName": "my_langs"     // OPTIONAL — defaults to sanitised file stem
}
----

When `register: true`, the response gains a `registered` block:

[source,json]
----
{
  "queryId":     "958c0130",
  "rowsWritten": 5,
  "resolved":    "s3://hitorro/queries/my-langs.parquet",
  "registered": {
    "tableName":       "my_langs",
    "typeJson":        "{\"name\":\"my_langs\",\"fields\":[…]}",
    "uri":             "s3://hitorro/queries/my-langs.parquet",
    "format":          "parquet",
    "broadcast":       true,
    "agentsNotified":  2
  },
  "elapsedMs": 697,
  "success":   true
}

See <<runtime-tables>> for how the fan-out to agents works.

Response:

[#common-use-cases]
== Common use cases

=== Real-time metrics dashboard

Streaming source (Kafka topic) → windowed aggregate → SSE to a dashboard.

[source,sql]
----
SELECT
    WIN_START(event_time, 60000) AS window_start,
    region,
    COUNT(*)                     AS requests,
    AVG(latency_ms)              AS avg_latency
FROM  events
GROUP BY WIN_START(event_time, 60000), region
----

Client consumes via SSE:

[source,bash]
----
curl -N "http://mesh/mesh/queries/stream?sql=$(python3 -c '
import urllib.parse, sys
print(urllib.parse.quote(sys.stdin.read()))
' <<'SQL'
SELECT WIN_START(event_time,60000) window_start, region, COUNT(*) requests
FROM events GROUP BY WIN_START(event_time,60000), region
SQL
)"
----

Each minute-window's aggregate row arrives as an SSE event as its
watermark passes.

=== Cross-shard reporting query

Docs sharded by region across N agents; report language coverage globally.

[source,sql]
----
SELECT lang, COUNT(*), AVG(size_kb)
FROM   docs
WHERE  size_kb > 10
GROUP BY lang
ORDER BY 2 DESC
LIMIT  20
----

Executes as a `TwoStagePlan`: partial aggregates per partition (WHERE
applied pre-shuffle), driver-side combine sums COUNT and re-averages
via SUM/COUNT decomposition, ORDER BY + LIMIT applied post-combine.

=== Enrich a fact table with a dimension

Events (distributed) joined with a small lookup (broadcast).

[source,yaml]
----
# driver.yml
hitorro.mesh.driver.broadcast-tables: [langs]

# Every agent's config also lists langs as a broadcast table:
hitorro.mesh.agent.broadcast-tables:
  - name: langs
    type-json-resource: file:/config/types/langs.json
    ndjson-file: file:/data/langs.ndjson
----

[source,sql]
----
SELECT e.doc_id, l.name AS lang_name, COUNT(*) AS hits
FROM   events e JOIN langs l ON e.lang_code = l.code
GROUP BY e.doc_id, l.name
----

=== Two fact tables joined

Both sides sharded — shuffle-hash join, optionally with GROUP BY.

[source,sql]
----
-- Simple join
SELECT d.id, d.title, e.action
FROM   docs d JOIN events e ON d.id = e.doc_id
WHERE  e.action IN ('view','download')

-- Aggregate on top
SELECT d.lang, COUNT(*) AS interactions
FROM   docs d JOIN events e ON d.id = e.doc_id
GROUP BY d.lang
----

=== Long-running ad-hoc report with a cancel button

Batch query that might take minutes. Client sends `retries: 1` for
transient recovery, keeps the returned `queryId`, and can `DELETE`
if the user cancels from the UI.

[source,bash]
----
qid=$(curl -sS -X POST http://mesh/mesh/queries \
      -H 'Content-Type: application/json' \
      -d '{"sql":"...heavy query...","timeoutMs":600000,"retries":1}' \
      --max-time 3 | jq -r .queryId)

# User clicks "cancel":
curl -X DELETE "http://mesh/mesh/queries/$qid"
----

=== Debug why a query picks the plan it does

Use the EXPLAIN endpoint to see the planner's decision without
executing the query:

[source,bash]
----
curl -s 'http://mesh/mesh/queries/explain?sql=SELECT+lang,+COUNT(*)+FROM+docs+GROUP+BY+lang' | jq .
----

Response includes `planType`, plan-specific fields (`partialSql`,
`combineSql`, `groupColumns`, join keys + kind, WHERE pushdown extract),
and per-partition `eligibleAgents`.

[#config-reference]
== Configuration reference

=== Driver — full property surface

Every field on `DriverProperties`. Bind via
`hitorro.mesh.driver.<field>` in `application.yml`.

[cols="1,1,3", options="header"]
|===
| Field | Type | Purpose

| `transport`
| `NATS` (default) or `INMEMORY`
| Wire transport. INMEMORY is single-JVM only; useful for tests.

| `natsUrl`
| String
| NATS URL, e.g. `nats://host:4222` or `tls://host:4222`.

| `natsSecurity`
| `NatsSecurityProperties`
| TLS + auth config (see below). Empty = plaintext, no auth.

| `agentExpiry`
| `Duration`
| Grace period after last heartbeat before an agent is considered dead.
  Default 15s.

| `shuffleWidth`
| int
| Combine workers per shuffle-heavy query. 0 = combiner-at-driver (phase 2);
  N&gt;0 = distributed combine.

| `broadcastTables`
| List<String>
| Names of broadcast dimension tables. Registers so JOIN validation
  knows they're allowed.

| `tables`
| List<TableConfig>
| Bootstrap set of distributed tables. See TableConfig below.
|===

*TableConfig.*

[cols="1,3", options="header"]
|===
| Field | Purpose
| `name` | logical table name used in SQL FROM
| `typeJsonResource` | Spring resource URL for the JVS type definition
| `partitions` | list of Partition entries (key + requiredCapabilities + approxRowCount)
|===

=== Agent — full property surface

Every field on `AgentProperties`. Bind via `hitorro.mesh.agent.<field>`.

[cols="1,1,3", options="header"]
|===
| Field | Type | Purpose

| `id`
| String (required)
| Unique agent identity within the mesh. Must be stable across restarts
  if the cluster manager expects it.

| `transport`
| `NATS` (default) or `INMEMORY`
| Same as driver.

| `natsUrl`
| String
| Same as driver.

| `natsSecurity`
| `NatsSecurityProperties`
| Same as driver. Set the *same* config on every mesh peer.

| `heartbeatInterval`
| `Duration`
| How often to publish `HeartbeatMessage`. Default 2s.

| `capabilities`
| List<String>
| What this agent advertises. Must include `jvssql` + a
  `partition:<table>:<key>` for every partition it holds. Can also be
  supplemented from `HITORRO_MESH_CAPABILITIES` env (comma-separated).

| `tables`
| List<TableConfig>
| Local tables this agent serves. Each entry has EXACTLY ONE source
  block: `ndjson-file` (batch), `kafka` (streaming), or `nats`
  (streaming).

| `broadcastTables`
| List<TableConfig>
| Small dimension tables that every agent pre-loads for broadcast
  JOINs. Same shape as `tables` but no `partitionKey`.
|===

*Agent TableConfig source blocks.*

[cols="1,3", options="header"]
|===
| Block | Fields
| `ndjson-file` (batch)
| Spring resource URL to an NDJSON file — one JSON per line
| `kafka` (streaming)
| `bootstrap-servers`, `group-id`, `topic`, `auto-offset-reset`,
  `auto-commit`, `max-poll-records`, `poll-timeout`
| `nats` (streaming, JetStream)
| `url`, `stream`, `subject`, `durable-name`, `batch-size`,
  `fetch-timeout`, `connect-timeout`, `ack-wait`
|===

=== NatsSecurityProperties — auth + TLS

Applies to both driver and agent under `nats-security:`.

[cols="1,3", options="header"]
|===
| Field | Purpose
| `username` + `password` | user/pass auth
| `token` | token auth (mutually exclusive with user/pass; token wins)
| `credentialsFile` | path to `.creds` file (nkey + JWT; strongest, wins over token)
| `tls` | force TLS even if URL is `nats://` (not `tls://`)
| `trustStorePath` + `trustStorePassword` + `trustStoreType` | PKCS12/JKS truststore
| `keyStorePath` + `keyStorePassword` + `keyStoreType` | mTLS client cert
|===

Auth precedence: creds > token > user/pass. TLS activates when *any*
of: `tls: true`, custom trust material, custom key material, URL
scheme `tls://`.

=== System properties (JVM `-D` flags)

[cols="2,1,3", options="header"]
|===
| Property | Default | Purpose

| `hitorro.mesh.driver.max-queue-rows`
| 100000
| Bounded result-queue cap per query. Overflow drops rows + logs WARN
  + bumps `mesh_backpressure_drops_total`.

| `hitorro.mesh.driver.max-task-retries`
| 1
| Per-partition surgical retries on ERROR (only if 0 rows emitted).
  0 to disable.

| `hitorro.mesh.watermark.idle-timeout-ms`
| 30000
| Streaming — advance watermark on wall-clock after idle. Very
  large = disable for backfill scenarios.
|===

[cols="2,1,3", options="header"]
|===
| Property | Default | Purpose

| `hitorro.storage.s3.endpoint`
| _(unset)_
| S3 API URL, e.g. `http://localhost:9000` for local MinIO or

| `hitorro.storage.s3.bucket`
| `hitorro`
| Default bucket used when a `s3://` URI omits the bucket, and target

| `hitorro.storage.s3.access-key`
| `hitorro`

| `hitorro-dev-only`

| `hitorro.storage.s3.ssl`
| `false`

| `hitorro.storage.minio.scripts-dir`

  "queryId": "3f21a8bc"
}

= Part V — Operations

[#health-checks]
== Health checks

Phase 7j added `MeshHealthIndicator` — a Spring Boot HealthIndicator
that surfaces mesh-specific health under `/actuator/health/mesh` and
composes into the top-level `/actuator/health` composite status.

*Statuses:*

* *UP* — every declared partition has ≥1 eligible agent
* *OUT_OF_SERVICE* — some partitions have zero eligible agents;
  queries touching them fail. Non-fatal (rolling deploy, agent restart
  mid-flight), but K8s should stop routing to this driver.
* *DOWN* — driver knows about tables but sees zero live agents at all.

*Details always included:*

[source,json]
----
{
  "status": "OUT_OF_SERVICE",
  "components": {
    "mesh": {
      "status": "OUT_OF_SERVICE",
      "details": {
        "liveAgents": 3,
        "registeredTables": 2,
        "registeredPartitions": 6,
        "broadcastTables": 1,
        "streamingTables": 0,
        "uncoveredPartitions": ["events:apac"],
        "reason": "some partitions have no eligible agents"
      }
    }
  }
}
----

*Recommended K8s probe config* (Helm chart does this):

* Liveness: `/actuator/health/liveness` (Spring built-in, JVM-only) —
  avoids restart-looping during partition outages
* Readiness: `/actuator/health` (composite, includes mesh) — removes
  the driver from the Service during OUT_OF_SERVICE so no traffic
  routes to a broken mesh

[#backpressure-and-retries]
== Backpressure and retries

*Query lifetime deadline* (<<retry-model>>): every query submitted
via `POST /mesh/queries` has a `timeoutMs` (default 5000). On expiry,
`CancelMessage` propagates to all agents; response includes
`timedOut: true`.

*Whole-query retry* (phase 7g): request body `{"retries": N}` retries
the entire query up to N times on `AgentTaskException` with
exponential backoff (100ms · 2^n). QueryTimeoutException and
IllegalArgumentException don't retry — those aren't transient.

*Task-level surgical retry* (phase 7k): on ERROR from a partition that
hasn't emitted any rows yet, re-dispatch that ONE partition's task
(new taskId, fresh agent pick). Bounded by
`-Dhitorro.mesh.driver.max-task-retries` (default 1). Runs *before*
the whole-query retry; the two compose (task retry succeeds silently,
whole-query retry catches what task retry couldn't).

*Backpressure* (phase 7i): per-query result queue is bounded at
`-Dhitorro.mesh.driver.max-queue-rows` (default 100k). On queue-full,
the subscription callback blocks for up to 1s then drops the row with
a WARN log + increment of `mesh_backpressure_drops_total`. Sentinels
(EOS, ERROR) never drop — consumers always see stream-end.

[#troubleshooting]
== Troubleshooting

*"no live agent advertises 'jvssql'"* — the driver's capability
lookup returned zero agents. Check `curl /mesh/agents` returns rows;
if not, agents aren't heartbeating (see agent logs — TLS, network,
config issue).

*"only registered broadcast tables can be joined"* — a JOIN
referenced a table the mesh doesn't know as distributed OR broadcast.
Register it distributed via `driver.tables` or broadcast via
`driver.broadcast-tables`.

*"shuffle-hash JOIN currently supports INNER and LEFT only"* — you're
running RIGHT / FULL. jvssql supports all four (phase 4c.1); make
sure `hitorro-jvssql >= 3.0.1`.

*Windowed streaming query stalls forever* — check the phase-6d.2.2
idle timeout. Default 30s; for backfill scenarios set very large.
See <<multi-partition-close>>.

*Query timeout on the REST response* — increase `timeoutMs` (default
5000). Check `mesh_query_duration_seconds` for the actual p99 to size it.

*Agent in `MISSING` state on `/mesh/cluster`* — the platform bridge
(Orion / K8s) declared an agent that hasn't heartbeated within
`agent-expiry` (default 15s). Check pod logs, NATS connectivity, TLS.

*`mesh_backpressure_drops_total` climbing* — a slow client (or slow
network to the client) is falling behind fast-producing agents.
Either speed up the consumer, raise `-Dhitorro.mesh.driver.max-queue-rows`,
or use SSE (streaming) so results push as they arrive.

*Partitioned answers off by a factor of N* — you registered the same
NDJSON file on multiple agents that all claim different partition
keys. Each agent scans the whole file → duplicate results. Ensure
each partition file only sits on the agent for that partition.

*Streaming aggregate output has `g0` / `c0` columns instead of my
aliases* — you're on `hitorro-mesh-driver < 3.0.1`. Phase 6d.2.3
preserves `AS foo` aliases through combine SQL.

*mTLS handshake fails with "unable to find valid certification path"*
— the JVM truststore doesn't contain the CA that signed the NATS
server cert. Add a PKCS12 truststore via `nats-security.trustStorePath`
(see <<tls-handshake>>).

*MinIO "Connection refused" on `http://localhost:9000`* — the
container isn't running. Click *▶ Start MinIO* on the Cluster tab, or
run `hitorro-mesh-examples/scripts/minio/minio-up.sh`. First start
takes ~30 s to pull the image; subsequent starts are seconds.

*Storage browser shows "Error" at the root* — the default browse root
was hard-coded to `s3://<bucket>/datasets/`; a fresh bucket has no
such prefix so S3 returned "not found". Fixed in driver-app 6ef4cae —
the default is now the bucket root and shows every top-level prefix
that actually exists.

*Playground write to `s3://` reports success but no object in bucket*
— the stock `NdjsonFileSink` is local-only; `Path.of("s3://…")` was
being treated as a POSIX path and files landed at `./s3:/bucket/…`.
Fixed in driver-app b2f386b — non-`file:` URIs route through
`BaseFileNdjsonSink` (via `BaseFile.getOutputStream()`). For Parquet:
`s3://` gets rewritten to `s3a://` with the driver's MinIO
credentials injected into a Hadoop `Configuration`.

*`Relative path in absolute URI: file:./queries/foo`* — `file:`
URIs require an absolute path per RFC 3986. Fixed in QueryWriteController
by absolute-ifying against `user.dir` before handing to the sinks.
Upgrade to driver-app 894f073 or later.

*Write + register succeeded but `SELECT * FROM <name>` says "does not
hold partition broadcast of table X"* — one or more agents failed to
install the table but didn't crash the write. Check agent logs for
`failed to register runtime table` lines. Common cause: agent is on
an older jar without `RuntimeTableInstaller` — rebuild + restart
`hitorro-mesh-agent-app` (needs commit 9767d14 or later).

*Register succeeded on agents but `SELECT` still fails with
"ClassNotFoundException: S3AFileSystem"* — the agent doesn't have
`hadoop-aws` on its classpath, so `s3://` URIs can't be read by
`NdjsonLocalTable` / `ParquetLocalTable`. Fixed in agent-app d9c890b
(the `hadoop-aws` dep was added). Rebuild + restart agents.

*Parquet install fails with "NoClassDefFoundError: FileInputFormat"*
— `ParquetReadOptions.Builder` references
`org.apache.hadoop.mapreduce.lib.input.FileInputFormat` in its static
init. Fixed by adding `hadoop-mapreduce-client-core` to the agent-app
pom (~1 MB extra).

= FAQ

[#faq]
== Frequently asked questions

*Q: What's the difference between the mesh and Spark or Flink?*

The mesh is much smaller (~65 MB fat jar vs ~800 MB Spark install),
runs on plain JVMs (no cluster manager required), and is
purpose-built for JSON documents typed by JVS. It lacks Spark's
cost-based optimizer, its ML libraries, and its multi-language
clients. See <<Comparison at a glance>>.

*Q: Do I need to write Java code to add a table?*

For most cases no — configure it in `application.yml` on the agent
side (batch: `ndjson-file`, streaming: `kafka` or `nats`). Custom
sources implement the `LocalTable` interface (four methods) — see the
Kafka / NATS adapter modules for ~30-line examples.

*Q: Can I query a table that lives in Postgres / MySQL / MongoDB?*

Not out of the box. The mesh's `LocalTable` interface expects a
`Iterator<JVS>`; if you can wrap a JDBC/Mongo query as a JVS iterator,
you can plug it in. That's how the Kafka and NATS streaming adapters
work — they wrap `hitorro-streams-kafka`'s `KafkaSource.asJvsIterator()`.

*Q: What happens if an agent dies mid-query?*

The task fails with an ERROR that the driver receives. Phase 7k
surgical retry re-dispatches that partition on another eligible agent
(if any; if the partition is on only one agent that died, retry same
agent after backoff). If no retries remain, phase 7g whole-query
retry kicks in (if the client requested it). Otherwise the client sees
`AgentTaskException` / 502 Bad Gateway.

*Q: Can I run queries across multiple mesh clusters?*

Not directly. Each mesh has one driver + N agents talking over ONE
NATS broker. To federate, you'd add cross-mesh JOIN logic yourself
(e.g., pull results from mesh A via REST, register as a broadcast
table on mesh B). Or run one big mesh instead.

*Q: How much data can the mesh handle?*

Depends on the per-partition size (bound by agent JVM heap for the
biggest query result on that partition) and the combine memory (bound
by driver heap for aggregate combine). Streaming queries have bounded
per-window state (jvssql closes windows on watermark advance).
No hard limits in the code — practical limits are JVM heap and
network bandwidth to your NATS broker.

*Q: Does the mesh do any query optimization?*

Yes but simple: regex-based planner that picks the plan variant
(<<plan-variants>>). Doesn't reorder joins, doesn't estimate
cardinality, doesn't consider partition skew. WHERE pushdown to
per-side scans is applied. For anything more sophisticated, write the
query with the join order you want.

*Q: What SQL features aren't supported for distribution?*

Streaming JOIN (planned phase 8), subqueries in WHERE / SELECT,
window functions (`OVER PARTITION BY`), PIVOT/UNPIVOT, CTEs
(`WITH x AS ...`), correlated queries, multi-statement transactions.
See <<SQL cheat sheet>> for what IS supported.

*Q: Can I do transactions?*

No. The mesh is read-only (query-only). Writes happen at the source
of truth (Kafka, database, whatever backs your `LocalTable`).

*Q: How do I secure the REST endpoints (Bearer auth, OAuth)?*

The mesh doesn't ship auth on the REST surface. Front it with an
ingress / API gateway (nginx, Envoy) that terminates auth before
forwarding to the driver. Or add a Spring Security filter — the
driver-app is a plain Spring Boot app.

*Q: Can I scale the driver horizontally?*

You can run multiple drivers, but they don't coordinate — each has
its own view of live agents (both would see all heartbeats, both
would compete to dispatch). For load-shedding + failover, run 1
primary + 1 standby behind a `PodDisruptionBudget` and put a proxy
in front that fails over on the primary going down.

*Q: How do I upgrade a mesh cluster?*

Rolling deploy of agents first (mesh remains up; readiness probes
gate traffic during pod restart), then driver. `MeshHealthIndicator`
reports OUT_OF_SERVICE during the window when partitions are
uncovered — the K8s readiness probe removes the driver from the
Service so no queries fail.

*Q: Can I have per-tenant isolation?*

Not built in. You could run one mesh per tenant (each with its own
NATS subject prefix) or embed tenant filtering in every SQL query
(app-layer). No mesh-level ACLs.

*Q: How do I add a new metric?*

Driver-side: add to `MeshMetrics` (Spring `@Component` — get a
`MeterRegistry` injected, register your gauge/counter). Agent-side:
add a lifetime counter on `MeshAgent`, an atomic increment at the
right lifecycle point in `TaskExecutor`, and a corresponding gauge
registration in `MeshAgentMetrics`.

*Q: The mesh looks great — where's the biggest limitation?*

Two: (1) streaming JOIN between two streaming sources isn't
implemented (batch JOIN + windowed aggregate work fine). (2) no
built-in write path — writes happen upstream of the mesh.

= Glossary

[#glossary]
== Terms

*Agent* — a JVM process that runs one or more `LocalTable`
instances and heartbeats to the mesh driver. Executes jvssql queries
against its local partition slice.

*AgentTaskException* — typed error raised when an agent reports an
`ERROR` ResultMessage during a query. Maps to HTTP 502.

*Backpressure* — the mechanism (phase 7i) that bounds the driver's
result queue: on overflow, rows are dropped with a WARN log +
metric increment.

*Broadcast table* — a small dimension table replicated to every
agent, referenced from JOINs. Every agent must pre-load it in its
config.

*Cancel message* — driver → agents wire message that interrupts
in-flight tasks for a given queryId.

*Capability* — a string tag advertised by an agent in its heartbeat
(`jvssql`, `partition:docs:us`). Drivers match tasks to agents by
capability set.

*Combine* — the reduce step that follows a shuffle. Runs at the
driver (`submitTwoStage`) or at N combine-worker agents
(`submitTwoStageShuffle` / `submitShuffleJoinAggregate`).

*Combine spec* — wire DTO carrying the shuffle input subjects,
per-side type JSON, and join kind that a combine worker needs.

*Distributed table* — driver-side view of a partitioned table.
Registered in `DistributedTableRegistry`; the planner uses it to
plan JOIN variants.

*EOS* — end-of-stream. `ResultMessage.Kind.EOS` signals a partition
finished emitting. The driver counts EOSes to know when a query is
complete.

*Idle-timeout watermark* — phase 6d.2.2 mechanism that advances a
partition's watermark on wall-clock when the source is silent
beyond `hitorro.mesh.watermark.idle-timeout-ms`.

*JVS* — JSON Value Set. The typed JSON document format used
throughout the Hitorro stack, produced by `hitorro-jsontypesystem`.

*jvssql* — Apache Calcite-based SQL engine that operates over
`Iterator<JVS>`. Runs embedded in every agent.

*LocalTable* — agent-side interface with four methods
(`name`, `type`, `partitionKey`, `openScan`) + optional
`streamConfig`. Implementations wrap NDJSON files, Kafka topics,
JetStream subjects, or in-memory queues.

*Mesh* — colloquial term for "one driver + N agents talking over
one NATS broker."

*Multi-partition close detection* — phase 6d.2 driver-side logic
that decides when a streaming window is closed globally across all
partitions. Combines row emissions + watermark heartbeats +
idle-timeout signals.

*Partition* — a single shard of a distributed table, hosted by one
(or more, for redundancy) agents. Identified by a partition key.

*Partition key* — a string chosen by the deployer that uniquely
identifies which shard of a table an agent holds (e.g., `us`, `eu`,
`shard-0`).

*Plan* — sealed interface with variants for each supported query
shape (`SimplePlan`, `TwoStagePlan`, `ShuffleJoinPlan`,
`ShuffleJoinAggregatePlan`, `StreamingWindowedPlan`).

*Query timeout exception* — typed error raised when a query
exceeds its `timeoutMs` deadline. Maps to HTTP 408.

*Result message* — agent → driver wire message. Four kinds: ROW,
EOS, ERROR, WATERMARK.

*Shuffle bucket* — a hash-partition-target of a shuffle stage.
Rows with the same hash(key) mod N land in the same bucket for
downstream join / aggregate.

*Shuffle-hash join* — join between two distributed tables where
both sides hash-partition by their join key, and per-bucket
combine workers do the actual join.

*Streaming table* — a `LocalTable` (or `DistributedTable`) whose
`streamConfig()` is non-null, signaling that jvssql should use its
incremental `StreamingAggregate` executor for windowed queries over
this source.

*Task descriptor* — driver → agent wire message. Carries the SQL
to run, source table + partition key, required capabilities,
result subject, optional shuffle spec, optional combine spec.

*Two-stage plan* — plan variant for GROUP BY / aggregate without
JOIN. Per-partition partial aggregate + combine.

*Watermark* — an event-time timestamp beyond which no more events
are expected. Drives incremental window emission in streaming
queries.

*Watermark tracker* — agent-side helper (phase 6d.2.1) that
observes `event_time` on rows and exposes running max. Wrapped
around the source iterator by `TaskExecutor` for streaming scans.

*Window function* — one of `WIN_START`, `WIN_END`, `WIN_HOP_STARTS`
(from `hitorro-jvssql`) that computes a window boundary from an
event timestamp.
